    - POST `{baseURL}/events` with one well-formed synthetic `company.started` event -> 202; POST the identical event again -> 202 again (proves the deployed dedup path behaves the same as Plan 01's local proof).
    - GET `{baseURL}/admin/workers` with no `X-Bootstrap-Secret` header -> 401.
    - POST `{baseURL}/admin/workers` with the correct `X-Bootstrap-Secret` and a `{ label: "e2e-staging-worker" }` body -> 201; capture the returned `workerId`/`token`.
    - GET `{baseURL}/admin/workers` with the correct secret -> the response array contains the new worker by id, and no item anywhere in the array contains a `secretHash` or `token` field.
    - Using the `ws` package directly (imported in this spec file, not the browser `WebSocket` global — same reasoning as Plan 02's ws-auth.test.ts: custom headers require the `ws` client), open a connection to `{wss version of baseURL}/ws` with no Authorization header -> rejected before `open`; open a connection using the captured `token` -> `open` fires.
    - POST `{baseURL}/admin/workers/{workerId}/revoke` with the correct secret -> 200; then attempt a NEW WS connection with the same token -> rejected.
  </action>
