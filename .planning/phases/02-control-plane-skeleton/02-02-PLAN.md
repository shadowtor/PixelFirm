<objective>
Build the WS gateway's authentication path (SEC-02): `GET /ws` only completes the upgrade handshake for a request carrying a valid, unrevoked, per-worker credential, validated in a `preValidation` hook that runs before Fastify sends the 101 response — never a raw `ws` `verifyClient` callback. Credential issuance mechanics (D-03, locked): a high-entropy `{workerId}.{secret}` token, with only an HMAC-SHA256 hash of the secret ever persisted.

Purpose: SEC-02 requires per-worker credentials that are unique and revocable, checked before the WS connection is ever established. This plan builds the auth primitives and the gateway itself; Plan 03 builds the admin routes that actually issue/list/revoke these credentials (this plan seeds test credentials directly via the DB, since no admin surface exists yet).
Output: `workers` table; `issueCredential`/`verifyCredential` helpers; an authenticated `/ws` route; a green integration test proving invalid/unknown/revoked credentials never complete the upgrade and a valid one does.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Worker (Phase 3+ real, synthetic client this phase) -> GET /ws upgrade | The credential in the Authorization header is the only trust signal; nothing else authenticates the caller |

| T-02-05 | Information Disclosure | apps/api/src/auth/credentials.ts (verifyCredential) | high | mitigate | `crypto.timingSafeEqual` on length-normalized buffers, never `===` or a manual byte loop — RESEARCH.md Pitfall 5 names this exact risk for the parallel bootstrap-secret comparison in Plan 03; this plan's `verifyCredential` is the shared primitive both routes call |
