<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worker credential -> POST /events / GET /ws | Same Phase 2 boundary, reused unchanged: an authenticated-but-untrusted worker process crosses into the control plane |
| worker.heartbeat payload -> connection-status registry | A worker-controlled JSON payload could claim to be a different workerId than its credential authenticated as |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Spoofing | apps/api/src/routes/events.ts heartbeat branch | high | mitigate | Key recordHeartbeat by the AUTHENTICATED `request.workerId` (set by worker-auth.ts's preValidation), never by `event.payload`'s (client-controlled) field — a worker cannot report presence on another worker's behalf |
| T-03-02 | Information Disclosure | apps/api/src/routes/admin-workers.ts | low | accept | The new `status` field is exposed only behind the existing bootstrap-secret gate (unchanged), same trust level as the rest of the endpoint |
| T-03-03 | Denial of Service | worker.heartbeat ingestion | low | accept | worker.heartbeat reuses the existing POST /events rate limit (300/min per Phase 2) — no new unlimited endpoint introduced |
| T-03-04 | Spoofing | apps/api/src/routes/ws.ts (Phase 2 gap, inherited) | medium | accept | A revoked worker credential's already-open socket is not force-closed (Pitfall 5) — no UI drives revocation until Phase 6's CEO dashboard exists; documented, not fixed this phase |

</threat_model>
