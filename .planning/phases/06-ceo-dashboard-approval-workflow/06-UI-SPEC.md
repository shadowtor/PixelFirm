# Phase 6 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

Two UI surfaces ship in this phase, with different rules:

1. **`/ceo` dashboard** (`apps/web`, new): a private React forms/list UI. This is where shadcn + Kibo UI apply.
2. **CEO room on the office canvas** (`packages/pixel-office`, extends Phase 5): pixel-art, governed by `05-UI-SPEC.md`. Nothing in the Phase 5 contract is re-decided here. This phase adds a room, a queue, and one walk.

**Privacy wall (D-08, D-09, locked):** decision title, context, recommendation, tool input, links and diffs render **only** on `/ceo`. The canvas shows only what Phase 5 already shows for `waiting_for_ceo`: the frozen pose and the amber `?` glyph, now in the CEO room. There is no text, label, bubble or dialogue on the canvas for a CEO decision.

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn (initialized by this phase's first UI task; not present today) |
| Preset | not applicable. Run `npx shadcn@4.21.0 init --base radix --css-variables --no-rtl --pointer --no-monorepo -c apps/web`, then replace the generated theme variables with the Color tokens below |
| Component library | radix (`--base radix`, because the Kibo UI `choicebox` depends on `radix-ui`) |
| CSS | Tailwind CSS v4 via `@tailwindcss/vite` (resolved 4.3.3 on 2026-09-24, from `npm view`) |
| Icon library | lucide-react (shadcn radix default; Kibo items depend on it) |
| Font | `ui-sans-serif, system-ui, sans-serif` for UI text, `ui-monospace, SFMono-Regular, Menlo, Consolas, monospace` for tool input and diffs. No webfont is loaded |
| Theme | Dark only. No light mode and no theme toggle |

**Why shadcn now, when Phase 5 was `Tool: none`:** Phase 5's UI was a Canvas2D renderer. `/ceo` is a real forms-and-list UI. The developer's locked `project-stack` default is Kibo UI (a shadcn registry) wherever a component exists, which means shadcn + Tailwind. Nothing in the repo overrides that (no `components.json`, Tailwind or PostCSS config exists; `apps/web` is React 19 + Vite 8).

**Scope isolation (hard rule):** Tailwind, shadcn and dashboard code must never load on the office route. The office route is what OBS captures in Phase 7.
- `apps/web/src/main.tsx` checks the path (D-08) and, when the path is `/ceo`, calls `import("./ceo/CeoApp")`. The office route keeps the static `App` import and loads nothing from `ceo/`.
- The Tailwind entry CSS (`ceo/ceo.css`, holding `@import "tailwindcss"` and the theme variables) is imported **only** from `ceo/CeoApp.tsx`. Vite then emits it with the lazy chunk. The init step writes a global CSS file and may add an import to `main.tsx`. Move that import into `ceo/CeoApp.tsx`.
- The shadcn `@/` alias resolves to `apps/web/src`. shadcn components land in `apps/web/src/components/ui/`, Kibo items in `apps/web/src/components/kibo-ui/`.
- `apps/web/index.html`'s `body` background (`#3A3A5C`, WALL_COLOR) stays unchanged. `/ceo` sets its own background on its root element.
- Check: a production build of the office route (`/`) contains no Tailwind preflight and no `ceo` chunk in its initial HTML/JS. A Playwright or asset-manifest assertion enforces this.

## Spacing Scale

Declared values (multiples of 4). These are Tailwind v4's default 4px spacing unit, so `p-1` = 4px, `p-2` = 8px, `p-4` = 16px, and so on.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gap, badge inner padding, diff gutter padding |
| sm | 8px | Gap between buttons in the action bar, queue-item inner line gap |
| md | 16px | Queue-item padding, detail section inner padding, header horizontal padding |
| lg | 24px | Gap between detail sections, detail pane padding |
| xl | 32px | Gap between queue column and detail pane (desktop) |
| 2xl | 48px | Empty-state vertical padding |
| 3xl | 64px | Unused this phase |

**Fixed sizes:**
- Header height 56px. Queue column width 360px at >= 1024px. Detail content max-width 880px.
- Buttons 36px tall (shadcn default `h-9`) at >= 768px. Below 768px, the action-bar buttons are 44px tall (touch target).
- Tool-input `<pre>` max-height 240px, then scrolls. Diff body max-height 480px per file, then scrolls.

**Exceptions:** Diff line box height is 18px (12px mono at line-height 1.5). The canvas keeps Phase 5's 16px tile grid (see CEO Room below), not the 4px DOM scale.

**Responsive layout:**
- **>= 1024px:** two panes. Queue list (360px, scrolls independently) on the left, detail on the right. The action bar sticks to the bottom of the detail pane.
- **768–1023px:** same two panes, queue column 300px.
- **< 768px:** one column. The queue is the page. Selecting an item shows the detail with a "Back to queue" link at the top. The action bar is fixed to the viewport bottom, and buttons wrap to two rows (Approve full-width on the first row).

## Typography

Three sizes, two weights.

| Role | Size | Weight | Line Height | Used for |
|------|------|--------|-------------|----------|
| Label | 12px | 400, or 600 for section headings | 1.4 | Meta lines (agent · task · waited), badges, section headings ("Recommendation", "Changes"), table header, diff/tool-input mono text (line-height 1.5 for mono) |
| Body | 14px | 400 | 1.5 | Context, recommendation, notes, queue-item titles, buttons (600), table cells |
| Heading | 20px | 600 | 1.25 | Decision title in the detail pane, empty-state heading, page title "CEO desk" |
| Display | n/a | n/a | n/a | Not used |

- Section headings are 12px/600, uppercase, letter-spacing 0.04em, in muted foreground.
- Queue-item titles are clamped to 2 lines (`line-clamp-2`). The detail title is never truncated.
- Mono text (tool input, diffs, file paths, decision id) is 12px. Diff and tool input wrap with `white-space: pre-wrap; overflow-wrap: anywhere`, so a long command never forces horizontal page scroll.

## Dashboard Layout & Interaction Contract (`/ceo`)

**Header (56px, `--card`, bottom border):** left, "CEO desk" (Heading) and the accent pending-count badge (hidden at 0). Right, Kibo `Status` ("Live" online / "Reconnecting" degraded / "Offline" offline), then the verified decider email from the Access JWT in muted Label. `document.title` is `(N) CEO desk · PixelFirm` while N > 0, otherwise `CEO desk · PixelFirm`.

**Tabs:** `Pending (N)` (default) and `History`.

**Queue item (Pending tab):** a `<button>` in a list, `aria-current="true"` when selected. Contents, top to bottom:
- Line 1 (Label, muted): agent name · kind badge · waited duration (`Intl.RelativeTimeFormat`, e.g. "12 min"; accent after 10 min).
- Line 2 (Body): decision title, 2-line clamp.
- Optional chip: `Round {n}` when the item belongs to a Discuss thread with earlier rounds.
- Order: oldest first (FIFO, the same order as the office queue). One item per `threadId`, showing its newest pending decision.
- The first item is auto-selected on load. When the selected item leaves the queue, the next item is selected. If none remain, the empty state shows.

**Kind badge:** `clarifying_question` shows the badge "Question". `ceo_gated_tool` shows "Gated action", followed by the matched pattern name from `classifySignal`'s reason in mono (for example `Gated action · git push`).

**Detail pane, top to bottom** (sections separated by 24px and a `separator`):
1. **Title** (Heading) plus a meta line (Label, muted): `{agent} · {task title} · {project} · waiting {duration} · #{decisionId first 8}`.
2. **Requested action** (gated tool calls only). Tool name as a mono badge, then the tool input summary in a mono `<pre>` (max-height 240px). The section heading reads "Runs on approve". This is the exact parked call (D-01): the UI never shows an edited or paraphrased version of what approval allows.
3. **Questions** (AskUserQuestion only). For each question (1–4): the header chip, the question text (Body), then options. Single-select uses Kibo `Choicebox`, with each card showing label (Body/600) and description (Label, muted). `multiSelect` uses checkbox cards in the same visual style. Every question also gets an "Other" option that reveals a textarea. The Approve button reads "Send answers" and stays disabled until every question has an answer. Option `preview` content, when present, renders in a mono `<pre>` under the selected card.
4. **Context.** The agent's context text as plain text (`white-space: pre-wrap`).
5. **Recommendation.** A `--card` block with the agent's recommendation as plain text, or the fixed empty copy (see Copywriting).
6. **Links.** A list of links. Only `http:`/`https:` URLs become anchors (`target="_blank" rel="noopener noreferrer"`). Any other scheme renders as plain mono text. The section is hidden when there are no links.
7. **Changes** (diff, D-09). A file list, one `collapsible` row per file: path (mono, truncate with `title` attribute), `+{added}` in success and `-{removed}` in error text. All rows start collapsed; above 3 files, the first file is expanded. The expanded body is the unified diff in a mono `<pre>` with per-line tints. When the worker's `truncated` flag is set, an `alert` above the list shows the truncation copy. With no diff attached, a muted single line shows the no-changes copy.
8. **Earlier in this thread** (Discuss threads only). A collapsed `collapsible`. Each earlier round shows: the CEO action badge, the CEO note, timestamp, and that round's request title.
9. **Action bar** (sticky, `--card`, top border, 16px padding):
   - "Note to agent" `textarea` (3 rows, auto-grow to 8), with helper text for which actions require it.
   - Buttons, left to right: **Approve** (default/accent), **Request changes**, **More research**, **Discuss** (all `outline`), then **Reject** (`destructive` variant rendered as outline: red border and red-on-hover fill, white text on hover), right-aligned.
   - Required note (D-07): Request changes, More research and Discuss stay **enabled**. Clicking one with an empty or whitespace note does not submit. Instead, focus moves to the textarea and the field shows the required-note error (`aria-invalid`, error text). Reject and Approve never require a note. A note typed before Approve or Reject is sent with the decision.

**Approve confirmation:**
- **Gated tool call:** Approve opens an `alert-dialog`. Its body repeats the tool name and the same input `<pre>`, so the CEO confirms against exactly what will run. Confirm = accent button, Cancel = outline. Focus starts on **Cancel**.
- **Question answers:** no dialog. "Send answers" submits directly.
- **Reject:** no dialog. One click (D-07). Rejecting fails closed and is always safe.

**No keyboard shortcuts** trigger any decision action. `Enter` in the note textarea inserts a newline and never submits. Accidental approval must need a pointer or Tab-and-activate on a labelled button.

**Submitting:**
- All five buttons and the textarea become disabled. The clicked button shows `spinner` plus its in-progress label.
- **On success:** the item leaves the queue, the next item is selected, and a `sonner` toast shows the success copy.
- **On failure:** the buttons re-enable, the note is kept, and an `alert` shows above the buttons.
- **On 409 or not-pending:** the detail pane swaps to the no-longer-pending `alert`, and the item leaves the queue on the next refresh.

**Live updates:**
- A new decision arriving appends to the queue and announces through an `aria-live="polite"` region (copy below). It never steals the current selection.
- A decision decided elsewhere, or expired, disappears from the queue. If it was selected, the detail pane shows the matching `alert`, and the draft note stays visible until the CEO moves on.
- Losing the live feed changes the Status to Reconnecting/Offline. Action buttons stay enabled, because decisions POST over HTTP independently of the feed.

**History tab:**
- A `table` of the latest 50 decisions, newest first. Columns: When (absolute local time, relative in `title`), Agent, Decision (title, 1-line truncate), Action (badge), Decided by (email), Note (1-line truncate; full note in `title`).
- Action badges: Approved (success outline), Rejected (destructive), Changes requested / More research / Discuss (neutral outline), Expired (muted, dashed border).
- Expired rows show a **Resume task** `outline` button (D-02: the CEO re-triggers the blocked task). It POSTs through the same Access-JWT + CSRF-protected API as decisions.
- History reads from the audit events (D-04, CEO-05). It is read-only apart from Resume.

**Accessibility baseline:**
- Every icon-only control has an `aria-label`.
- Tab order: header, tabs, queue, detail, action bar.
- The alert-dialog traps focus and returns focus to the Approve button.
- The detail pane's section headings are real `h3` elements under the `h2` title.
- Minimum text contrast is 4.5:1 (every token pair above meets it).
- Motion is limited to shadcn's default open/close transitions, all disabled under `prefers-reduced-motion`. No GSAP or Anime.js is added in this phase (YAGNI; nothing here needs choreographed motion).

## CEO Room Contract (office canvas, D-10)

Extends `05-UI-SPEC.md` without changing any of its locked rules: glyph format, glyph placement, frozen pose, status mapping, colour separation, and the dialogue rules.

**Grid:** `DEFAULT_COLS × DEFAULT_ROWS` goes from 20 × 11 to **24 × 13**. The office grows right and down only, so **every existing seat, standing spot, desk, monitor, decor and interaction coordinate is unchanged**.
- Why 24 × 13: 384 × 208 at scale 5 is exactly 1920 × 1040, so a 1920 × 1080 OBS source (Phase 7's target) keeps a full-width fill with a 20px WALL_COLOR strip above and below. Today's 20 × 11 fills it at scale 6 with 12px strips.
- Cost: 1280 × 720 drops from 4× to 3× (1152 × 624). Recommended OBS sizes become **1920 × 1040 (5×)** and 1920 × 1080.
- Every Phase 5 test or harness value derived from 320 × 176 must be re-derived from the constants, not hard-coded again.

**Tiles** (`office-layout.json` `tiles`, 24 chars × 13 rows):
- Row 0 and row 12 are wall. Col 0 and col 23 are wall.
- Col 19 is the room's partition wall on rows 1–11, **except a door at (19, 7)** (floor). The door sits on the existing row-7 lane.
- Main office floor: cols 1–18, rows 1–11. Rows 10–11 are new empty floor (a lane under the row-9 desks). No new seats are added this phase.
- CEO room floor: cols 20–22, rows 1–11.

**CEO room furniture:**
- The CEO desk is the existing `desk` sprite at `{col: 20, row: 10, w: 3, h: 1, blocks: true}`, with no monitor.
- Tile (21, 11) behind the desk stays empty. The CEO is the human and is never drawn as a character.
- At least one existing decor sprite (`plant`, `plantSmall`, `bookcase` or `painting`) goes in the room. Decor must not sit on a queue slot, the door (19, 7), the entrance tile (20, 7), or column 21 rows 4–9 (the walk path). No new sprite asset is required.

**Queue** (`office-layout.json` `ceoQueue`, in front-of-line order): `[[21, 8], [20, 6], [22, 6], [21, 4]]`, four slots.
- Every pair of slots is Chebyshev >= 2 apart.
- No slot's glyph box overlaps another slot's sprite box. Measured at the Phase 5 glyph anchor (11 × 13, 3px above the visible head), the closest case is the glyph of (21, 8) at x 338–349, clear of (20, 6) (x 320–336) and (22, 6) (x 352–368).
- Every slot stays reachable from the door while the others are occupied (via (21, 7) and (21, 5)).
- A guard test in the same style as Phase 5's `office-layout.json` guards asserts all three properties.

**Queue behaviour:**
- **Arrival:** an agent entering `waiting_for_ceo` walks, using the Phase 5 walk/pathfinding system, to the **lowest-index free slot**. On arrival it faces **DOWN** (toward the viewer and the CEO desk below it), stands full-body, and holds the Phase 5 frozen pose plus the `bubble-permission` glyph. The glyph shows from the moment the status changes, including during the walk, exactly as Phase 5 already does.
- **No shuffling:** when the front slot frees up, agents already waiting keep their slots. Each slot is held for its occupant's whole wait.
- **Overflow:** with all 4 slots taken, the 5th and later waiting agents stay at their own desk, seated, with the same glyph (D-10). No sixth slot, no waiting in the aisle.
- **Leaving:** after any decision, or on expiry, the agent's status leaves `waiting_for_ceo`. The glyph updates to the new status immediately, and the agent walks back to its own home (seat or standing spot) through the door. The slot is released when the walk starts.
- **Standing, not sitting:** queued agents stand. "Waiting-chair slots" (D-10) is the name of the layout data. No chair sprite is drawn in this phase (see UI Considerations).
- **No text:** nothing on the canvas names the decision, the tool or the reason. The glyph is the whole signal, as in Phase 5.

**Colour:** the room reuses the MetroCity floor, wall and desk sprites and WALL_COLOR. No new canvas colour is introduced.

## UI Considerations

Applicable state considerations resolved: 11 covered, 2 backstop, 1 unresolved

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| loading | queue + detail on first load | ✅ covered | While decisions load, the queue shows 3 `skeleton` rows and the detail pane shows a title-plus-3-block skeleton. No empty-state copy renders before the first response |
| empty | Pending queue | ✅ covered | Zero pending decisions renders the `empty` component with the "No decisions waiting" copy, and the pending badge and title count are hidden |
| empty | History, recommendation, links, diff | ✅ covered | History shows "No decisions yet". A missing recommendation shows its fixed copy. Links are hidden when absent. A missing diff shows "No file changes attached to this request." |
| error | load failure / auth failure | ✅ covered | Load failure renders the loading-error copy with a Retry button. A 401/403 renders the auth-failure page and never the queue |
| error | submit failure | ✅ covered | A failed decision POST keeps the item and note, re-enables actions and shows the submit-error alert. Nothing is marked decided client-side before the server confirms |
| partial | decision decided elsewhere / expired while open | ✅ covered | The selected detail swaps to the matching no-longer-pending alert. Action buttons are removed for that item, so a stale decision cannot be submitted |
